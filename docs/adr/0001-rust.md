# ADR 0001：使用 Rust 构建可移植内核

- 状态：Accepted
- 日期：2026-07-29

## Context（背景）

疆诚记忆需要在桌面、服务端和移动端之间共享同一套协议校验、事件构造、持久化与恢复语义。核心路径会处理长期驻留的数据、并发写入、加密 Blob 和跨语言绑定，因此必须同时控制内存安全、资源占用、二进制可移植性和错误边界。

运行时垃圾回收会引入不可预测的暂停和额外内存占用；为每种 SDK 分别实现存储内核又会产生语义漂移。核心逻辑还必须禁止未审计的内存不安全代码。

## Decision（决策）

使用 Rust 2024 Edition 构建共享内核，当前最低 Rust 版本为 1.85。协议、事件、存储和嵌入式门面拆分为独立 crate，并通过类型化 ID、显式错误和异步接口保持边界清晰。

核心 crate 设置 `unsafe_code = "forbid"`。未来只有 FFI 或平台绑定边界在无法避免时才可隔离使用 `unsafe`，且必须写明不变量并添加针对边界的测试。核心内核不依赖垃圾回收器；上层 SDK 负责把 Rust 的所有权、取消和错误语义转换为目标语言习惯。

## Consequences（影响）

- 同一套校验和持久化逻辑可以编译到多个目标，减少各 SDK 重复实现造成的差异。
- 所有权和类型系统在编译期阻止一批悬垂引用、数据竞争和标识符混用问题。
- 无 GC 不代表无延迟；SQLite 锁等待、文件同步、压缩和加密仍需显式度量与限制。
- 跨语言绑定需要稳定的协议对象和错误码，不能直接暴露内部 Rust 类型布局。
- 团队需要维护 Rust 工具链、目标平台构建矩阵和原生依赖兼容性。

## Rejected Alternatives（否决方案）

- **为每个 SDK 使用宿主语言重写内核**：实现速度看似更快，但事务、哈希和验证规则会逐渐分叉。
- **使用 Go 作为共享内核**：交叉编译成熟，但 GC 和 C ABI 生命周期不符合当前对嵌入式内核的控制要求。
- **使用 C/C++ 自研内核**：可移植但扩大内存安全审计面，不符合核心逻辑默认安全的约束。
- **仅提供远程服务**：无法满足离线、桌面和移动端的本地嵌入式部署目标。
